# Consent records + receipt downloads

Every accept / reject / customise click in cmp.js produces a consent
event. Events land in Cloudflare D1 (hot store, last ~90 days) and
are nightly-archived to the Laravel database (long-term, indefinite).
This page covers what's recorded, how to find a specific event, and
how to download a regulator-ready receipt.

## What's in a consent event

| Field                         | What it is                                                                                                                               |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                          | UUID generated by cmp.js at the moment of the click. Same on retries (idempotency key).                                                  |
| `anonymousId`                 | UUID identifying the visitor session. Persists in the consent cookie across visits until cookie expiry.                                  |
| `bannerConfigVersion`         | Integer version of the banner config that was live at the moment of consent. Lets you reconstruct what the visitor saw.                  |
| `bannerTextHash`              | Currently `v{bannerConfigVersion}` — a pointer rather than a content hash. The receipt embeds the full banner config snapshot for proof. |
| `categories`                  | Object `{ necessary, preferences, statistics, marketing }` with booleans for what was granted.                                           |
| `gcmSignals`                  | Object with the seven GCM v2 signals (`ad_storage`, `analytics_storage`, etc.) and their granted/denied state.                           |
| `eventType`                   | `granted` / `denied` / `changed` / `withdrawn`.                                                                                          |
| `occurredAt`                  | ISO timestamp client-side (the visitor's clock).                                                                                         |
| `countryCode`                 | ISO 3166-1 alpha-2 from `cf-ipcountry` on the edge. May be null if undetected.                                                           |
| `userAgentHash`               | Hashed UA string. Not the raw UA — privacy by design.                                                                                    |
| `ipHash`                      | Hashed IP. Same.                                                                                                                         |
| `domainId` / `organisationId` | Where the event came from. Tenant-scoped via Laravel's global scope.                                                                     |

Find events in the admin under **Consent log**. Filter by domain,
event type, anonymous ID, or date range. Pagination defaults to 25
per page (max 100).

## Receipt downloads

The consent log slideover (click any row to open) has a **Download
receipt** button with two format options.

### Signed JSON (recommended for compliance)

A self-contained JSON file with:

- All fields from the event above
- A snapshot of the banner config the visitor actually saw —
  resolved by `(domain_id, banner_config_version)`. If the historical
  row is gone (only the current published row exists), it falls back
  to the current published row with `snapshotNote: "current_published"`.
- Generation metadata: `generatedAt`, `generatedBy` (the operator's
  user ID), `signatureAlgorithm: "HMAC-SHA-256"`.
- An HMAC signature over the canonical JSON (keys sorted recursively,
  signature + signatureAlgorithm fields stripped before signing).

Anyone holding the platform's `CONSENT_RECEIPT_SIGNING_KEY` can
re-compute the signature to verify the receipt hasn't been tampered
with after export. The signing key is separate from
`BANNER_CONFIG_SIGNING_KEY` so rotating one doesn't invalidate the
other.

#### Verifying a JSON receipt

```bash
# Pseudocode — exact tool depends on your stack
RECEIPT=$(cat receipt-{event_id}.json)
SIG=$(echo "$RECEIPT" | jq -r '.signature')
BODY=$(echo "$RECEIPT" | jq 'del(.signature, .signatureAlgorithm)' \
  | jq --sort-keys --compact-output .)

# Recompute
EXPECTED=$(echo -n "$BODY" | openssl dgst -sha256 -hmac "$CONSENT_RECEIPT_SIGNING_KEY" -hex | awk '{print $2}')

[ "$SIG" = "$EXPECTED" ] && echo "valid" || echo "tampered"
```

The Laravel `ConsentReceiptSigner` does this server-side too — point
auditors at it if they want to round-trip-verify in PHP.

### PDF (human-readable)

A formatted PDF rendered from a Blade template with the same data as
the JSON, laid out as a one-page document with the signature at the
foot for offline verification. Use this when a regulator asks for
"the receipt" and you don't want to explain HMAC.

## Per-visitor bundle downloads

If a visitor's `anonymous_id` has multiple events (e.g. they accepted,
later withdrew, later changed preferences), you can download all of
them as a single bundle:

1. Filter the consent log by both `anonymous_id` and `domain_id`.
2. The "Download visitor receipt" button appears in the filter bar.
3. Pick JSON or PDF.

The bundle bundles every event in chronological order with the banner
config snapshots they reference. Single signature over the whole
bundle.

## REST surface

Every receipt + listing path the admin uses is also reachable from
scripts and CI. Tenant-scoped under Sanctum SPA auth.

```
GET  /api/consent-events                                   Paginated list, filter ?domain_id= ?anonymous_id= ?event_type= ?from= ?to=
GET  /api/consent-events.csv                               Streamed CSV bulk export (same filters)
GET  /api/consent-events/{event}/receipt?format=json|pdf   Single-event signed receipt
GET  /api/consent-events/receipts/by-anonymous-id?anonymous_id=…&domain_id=…&format=json|pdf
                                                           Per-visitor bundle receipt
```

The list endpoint returns paginated `ConsentEvent` resources (see the
admin's consent log table). The two receipt endpoints stream a file
with `Content-Disposition: attachment; filename=…` — call them from
a server-side context, save the response body, and you're done.

`format=json` is the regulator-verifiable artefact; `format=pdf` is
the human-readable rendering of the same data.

## Bulk CSV export

For tooling that needs the whole consent log — BI dashboards,
spreadsheet pivots, e-discovery exports — the consent log page has an
**Export CSV** button on the filter bar. It hits:

```
GET /api/consent-events.csv
  ?domain_id=...        (optional)
  ?anonymous_id=...     (optional)
  ?event_type=granted|denied|changed|withdrawn   (optional)
  ?from=YYYY-MM-DD      (optional)
  ?to=YYYY-MM-DD        (optional)
```

Same filter surface as the list endpoint, so any query you can run in
the admin can be exported. Response is streamed via a DB cursor so
even multi-million-row exports don't OOM the API.

Columns are stable wire-format:

```
id, occurred_at, domain_id, organisation_id, banner_config_version,
anonymous_id, event_type, country_code, categories, gcm_signals,
banner_text_hash, user_agent_hash, ip_hash, created_at
```

`categories` and `gcm_signals` JSON-encode into a single CSV cell each
so the grid stays flat. To unpack: `JSON.parse(row.categories)` in any
spreadsheet macro or BI tool that handles nested JSON.

::: warning Use receipts for legal proof, not the CSV
The CSV is unsigned — fine for analytics, BI, internal audit. For
regulator submissions ("prove this visitor consented"), download a
signed [per-event](#receipt-downloads) or
[per-visitor](#per-visitor-bundle-downloads) receipt instead.
:::

## Data retention

- **D1 (Cloudflare hot store)**: bounded by the nightly archive job
  that drains events older than ~90 days. Use D1 for high-volume reads
  of recent events.
- **MySQL (Laravel archive)**: indefinite by default. Events sit here
  until you explicitly delete them (which only happens via
  cascade-delete from the parent domain — see
  [Managing domains → Deleting a domain](./managing-domains#deleting-a-domain)).

### Configurable retention per organisation

Each organisation has a `consentRetentionDays` field (NULL by default
= retain indefinitely; positive integer = delete events older than N
days). Set via the `PATCH /api/organisations/{id}` endpoint:

```bash
curl -X PATCH https://api.effectinsight.com/api/organisations/<uuid> \
  -H "Content-Type: application/json" \
  -H "Cookie: <sanctum-session>" \
  -d '{ "consent_retention_days": 365 }'
```

A daily `consent-events:purge` command runs at 02:00 UTC (offset from
the 03:00 archive job so they never race for the same rows) and
hard-deletes anything past the threshold for every org that has one
configured. Run it ad-hoc with:

```bash
php artisan consent-events:purge
```

The command is idempotent — re-running with the same data is a no-op
once the rows are gone. Output reports the per-org delete count + the
cut-off timestamp it used.

::: warning Hard delete
The purge bypasses receipts + the archive — deleted events cannot be
re-downloaded. Keep the retention window generous enough to satisfy
your regulator's bar (UK ICO guidance is "indefinite while consent is
in force" — typically the rePromptAfterDays window is the lower bound).
:::

## What's NOT in a receipt

- The raw IP address (only the hash).
- The raw User-Agent string (only the hash).
- The visitor's identity beyond `anonymous_id` — Effect Insight doesn't
  know who the visitor is.
- Linking to other systems (CRM, support tickets, etc.) — out of scope.

If a regulator asks for "the personal data we hold on this visitor",
the consent record itself contains no directly-identifying personal
data; the records exist _as proof that consent was correctly recorded_
for a session-scoped anonymous identifier. Your CRM / analytics
exports are separate questions.
